## Agent 1 — Auth / IAM / Cross-cutting Security

### A1-01 — Student-role user with no linked Student record hangs the Enrollment page
- **Severity:** Medium · **Category:** Error-handling / Performance
- **Where:** `/enrollment` (frontend EnrollmentPage); `GET /api/students/me` → 404
- **Repro:** Log in as a Student-role user that has no linked Student domain record (e.g. a freshly
  created `student` user). Open `/enrollment`.
- **Expected:** A friendly message ("we couldn't find your student profile, contact the registrar")
  and the page settles.
- **Actual:** Page is stuck on "Resolving your student record..." indefinitely with dropdowns disabled,
  and `GET /api/students/me` is retried repeatedly (observed 4 identical 404 calls) — a failing-call loop.
- **Graceful verdict:** (1) data correct: Y — (2) friendly message: N (infinite spinner, no guidance) — (3) UI usable: N (stuck).
- **Suggested fix:** On 404 from `/api/students/me`, stop retrying and render an explanatory empty state.
- **Update:** Confirmed this only affects a Student-role user with NO linked Student record. A properly
  linked student (`student`/studentID 11) loads `/enrollment` fine (200, shows enrolled CS101+CS210). So
  the defect is the unhandled 404 + retry loop, not enrollment itself.

### A1-02 — CRITICAL: any Instructor can grade ANY submission (broken object-level authz / mutation IDOR)
- **Severity:** Critical · **Category:** Security
- **Where:** `POST /api/submissions/{id}/grade` — `EduLearn.API/Controllers/SubmissionsController.cs` (~line 150-216). The handler checks only `grader.Role == Instructor || ITAdmin`; it never verifies the caller owns the section the submission belongs to.
- **Repro:** Token for `instructor` (userID 31, owns **zero** sections). `POST /api/submissions/1/grade {"score":7}` where submission 1 belongs to a section taught by graderID 7. Result: **HTTP 200**, score changed **85 → 7**. (Restored to 85 after test.)
- **Expected vs Actual:** Expected 403 (not your section). Actual 200, grade overwritten; a GradeChange audit row is written under the wrong instructor.
- **Graceful verdict:** (1) data correct: **N — grade corrupted by unauthorized user** — (2) friendly msg: n/a — (3) UI usable: n/a.
- **Evidence:** `score BEFORE 85.0` → `POST .../grade -> 200` → `score AFTER 7.0`.
- **Suggested fix:** In the grade handler, load the submission→assessment→section and require `section.InstructorFK == callerId` (allow ITAdmin override). Apply the same ownership check to re-grade.

### A1-03 — HIGH: any Instructor can read ANY submission (object-level read IDOR)
- **Severity:** High · **Category:** Security
- **Where:** `GET /api/submissions/{id}` — SubmissionsController.
- **Repro:** `instructor` (userID 31, no sections) → `GET /api/submissions/1` → **200** with full data (studentName "Student1", score, `fileURI`, graderName). Submission belongs to another instructor's section.
- **Expected vs Actual:** Expected 403/404 for a non-owning instructor. Actual full disclosure of another instructor's student's submission + file link.
- **Graceful verdict:** (1) data correct: Y — (2) friendly: n/a — (3) usable: n/a — but **confidential data leaked**.
- **Suggested fix:** Same section-ownership check on read; students may read only their own, instructors only their sections', ITAdmin all.

### A1-04 — Login/validation hardening: PASS (no defect)
- Empty submit → native + custom "cannot be blank". SQL `' OR '1'='1` and bad password → clean **"Invalid username or password"** (no SQL exec, no 500, no leaked status code/route). Protected deep-link `/users` while logged out → redirected to `/login`. Recorded as PASS for evidence.

### A1-05 — MFA not enforced for privileged roles
- **Severity:** Medium · **Category:** Security
- **Where:** /users (admin view); all 36 users show MFA = "Off", including every Registrar, Finance, ITAdmin, Auditor, DeptAdmin.
- **Detail:** The audit brief states the five privileged roles are meant to be TOTP-MFA-challenged at login. In the running system MFA is disabled for all of them and they log in with username/password only. Either MFA enforcement for privileged roles is not implemented/active, or it is opt-in and no privileged account has enrolled.
- **Graceful verdict:** n/a (design/security gap, not a crash).
- **Suggested fix:** Enforce MFA enrollment for privileged roles (block privileged actions until enrolled), or document that MFA is opt-in for this scope.

### A1-06 — User list has no pagination
- **Severity:** Low · **Category:** UI-UX / Performance
- **Where:** /users — renders all 36 users in a single ungrouped table ("Showing 36 of 36"). No page size cap.
- **Detail:** Fine at 36 rows; will degrade (DOM size, scroll) as the user base grows. Other list pages should be checked for the same.
- **Suggested fix:** Add server-side pagination / a page-size cap to the users table (and audit other large lists).

### A1-07 — CRITICAL: Students cannot search for sections (enrollment broken)
- **Severity:** Critical · **Category:** Security / Functional-bug
- **Where:** Enrollment page `/enrollment`, section search feature
- **API:** `GET /api/sections/course/{courseId}/term/{term}` → **403 Forbidden**
- **Repro:** As Student role, navigate to `/enrollment`, select any course (CS201, EE101, MA101) + any term (2026-Spring, 2026-Fall), click Search.
- **Expected:** List of available sections for enrollment.
- **Actual:** Error alert "Access denied - Your account doesn't have access to this." + "No sections found for the selected course and term."
- **API response:** `{"error":"You don't have permission to perform this action.","code":"FORBIDDEN","statusCode":403}`
- **Impact:** The entire enrollment search workflow is non-functional. Students cannot browse or enroll in new sections. Only pre-existing enrollments work.
- **Graceful verdict:** (1) data correct: n/a — (2) friendly: N (error message doesn't explain why Students can't search sections) — (3) usable: N (feature completely broken).
- **Suggested fix:** Grant Student role read access to `GET /api/sections/course/{courseId}/term/{term}`. Students must be able to search for open sections to enroll.

### A1-08 — Assessment detail page shows incorrect submission status
- **Severity:** Medium · **Category:** Data-correctness / UI-UX
- **Where:** Assessment detail page `/assessments/{id}` (tested with id=7, CS101 Quiz 1)
- **Repro:** As Student (studentID 11) who has already submitted and been graded for assessment 7 (submission #8, graded 42/50), navigate to `/assessments/7`.
- **Expected:** Page shows "You have already submitted" + submission details (score 42/50, graded status) + optionally a "Resubmit" button if allowed.
- **Actual:** Page shows "Total Submissions: 0", "You have not submitted this assessment yet", "Submit Now" button, and "My Submission: 0 submission(s)" — all WRONG.
- **Evidence:** `/submissions` page correctly shows submission #8 (CS101 Quiz 1, graded 42/50, submitted 6/1/2026 11:12:05 AM). When clicking "Submit Now" from assessment detail, API returns 400 "Student has already submitted for this assessment" (correct rejection, but confirms submission exists).
- **Graceful verdict:** (1) data correct: N (displays 0 submissions when ≥1 exists) — (2) friendly: N (misleading "Submit Now" when already submitted) — (3) usable: N (confusing, blocks resubmission understanding).
- **Suggested fix:** Assessment detail page must fetch and display the current user's existing submissions for that assessment, including status and score.

### A1-09 — Term mismatch across UI (Dashboard vs actual enrollments/sections)
- **Severity:** Low · **Category:** Data-correctness / UI-UX
- **Where:** Dashboard (Student + Instructor + Registrar), Enrollment page, Timetable
- **Detail:** Student Dashboard shows term badge **"2026-SPRING"** (top-left of main area), but:
  - Enrollment page shows student's 2 enrollments in term **"2026-Fall"** (CS101, CS210)
  - Timetable defaults to "2026-Spring" (shows 0 sections), must manually change to "2026-Fall" to see the 2 enrolled sections
  - Similarly, Instructor Dashboard header shows "2026-Spring" but all 3 instructor sections display term "2026-Fall"
  - Registrar Dashboard shows "2026-SPRING" but reports "SECTIONS: 0 (2026-Spring)" — the seed sections are all 2026-Fall
- **Impact:** Confusion — the "current term" badge doesn't match the actual term of active enrollments/sections. Students/instructors see empty state until they manually change the term filter.
- **Graceful verdict:** (1) data correct: Y (the enrollments/sections ARE in 2026-Fall) — (2) friendly: N (misleading current-term indicator) — (3) usable: Partial (works once user changes term, but initial state is confusing).
- **Suggested fix:** Either (a) update the "current term" logic to detect the term with active enrollments/sections and show that, or (b) seed data should create enrollments/sections in 2026-Spring to match the hardcoded dashboard badge.
